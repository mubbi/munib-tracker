# Proof log: Qur'an pronunciation assessment (NF-3.24, D3 / D18 / D20 / D23 / D24 / D25)

- **Feature:** after the person reads the ayah on screen aloud, each word comes back **Clear / Listen again / Not sure** (or, in the D24 fallback, **Heard / Skipped or unclear / Not sure**), with the reciter's word audio one tap away. No score, percentage or grade; the app never calls a recitation "correct", "valid" or "wrong". It runs the pinned FastConformer CTC model **on the device** (D3): never OS or cloud speech recognition, and audio never leaves the device or touches disk.
- **Code:** `apps/app/src/lib/quran-pronunciation/*` (lattice, forced aligner, GOP, verdict, calibration, session, summary, flagged-words API, pipeline), `apps/app/src/hooks/use-pronunciation-check.ts`, `apps/app/src/components/quran/pronunciation-check-session.tsx` (route `/quran/practice/session?mode=pronunciation`), `PracticeWordRow` (`pronunciation` prop), "Check" on the ayah card / ayah action sheet, "Check pronunciation" on the practice hub, `stores/pronunciation-calibration-store.ts`; eval `apps/app/scripts/quran-pronunciation-eval.mjs` (`pnpm --filter app quran-pronunciation:eval`, local only, not CI).
- **Shared stack (NF-3.20):** uses `lib/speech/fastconformer.ts` `openFastConformerRunner` / `createFastConformerRunner` and `lib/speech/mic-owner.ts` as-is (mic owner id `pronunciation`). No runner code was forked or edited; the lattice / alignment / GOP code is new and lives beside it in `lib/quran-pronunciation/`.
- **Review:** AI proof-backed review (D11), 2026-11-24.
- **Scripture in the UI:** none typed. The ayah and its words are the bundled text / Quran.com study words already used by Qur'an practice. The copy lines below are guide copy (paraphrase) with references; the expected text for alignment is `text_clean` from the model's own pinned `quran.json`.

## 2. Model / token facts (spike S4, token compatibility)

- **Files:** the D18 pinned FastConformer set (`fastconformer_full_mixed.onnx`, `vocab.json`, `quran_ctc_tokens.json`, `quran.json`, `export_metadata.json`), sha256-checked, web from the Hugging Face mirror (`webHosted: true`). A user who downloaded FastConformer for practice or hands-free tasbeeh downloads nothing new.
- **`quran_ctc_tokens.json` vs `vocab.json`:** every id is inside the pinned vocab (max id 1023, vocab 1025, blank 1024). Decoding each `surah:ayah:ayah` sequence through the vocab gives the model corpus' `text_clean` **exactly for 4,508 / 6,236 ayahs**, and for **1,514 more the only difference is the small waw / yaa marks (ۥ ۦ) encoded as `<unk>`** (2,466 `<unk>` ids in total); 214 differ in other small ways. So the token file _is_ compatible with the pinned vocab.
- **But a single canonical segmentation is the wrong target.** The pinned model is the "mixed" build and emits diacritised pieces (`▁الْ`, `لَ`, pure-harakat pieces) as well as bare ones (also found by NF-3.20). A first eval pass that forced the canonical `quran_ctc_tokens` sequence (quick set, Alafasy, 8 ayahs) gave reference recitations a median alignment score of −5.5 per token and word-boundary errors of p50 175 ms / p90 780 ms. **Decision:** like the NF-3.20 spotter, the aligner searches a **lattice** of every vocab piece that matches the folded `text_clean` (harakat, Qur'anic marks, tatweel and alifs removed; alif / hamza forms, ة→ه, ى→ي unified; alif-only and harakat-only pieces become fillers). On the same quick set the median score became 0.0 per piece and every different-passage negative was rejected. The token file is therefore not used at runtime; the version lock is on the vocab and corpus hashes (`ayah-tokens.test.ts`).
- **Scores** are normalised per emitted piece, not per frame (NF-3.20 finding: per-frame normalisation lets silence match).
- **Basmala:** the corpus prepends the basmala to ayah 1 of every surah except 1 and 9; those words are optional — the aligner tries both and never flags them.

## 3. Spike S3 / S4 evaluation (D23)

**All numbers are "measured on reference + synthetic audio".** They are not a claim about real learners' voices, and the app copy never makes one.

- **No new recordings, no storage of our own.** `pnpm --filter app quran-pronunciation:eval` builds the set at eval time from audio the app already streams: everyayah recitations by **Alafasy, Husary, Minshawi (murattal), Abdul Basit (murattal)** for 29 ayahs (Al-Fatihah 2–7, 2:2, 2:3, 2:5, 2:21, 2:201, 3:8, 17:24, 18:10, 20:25, 20:114, 23:2, 36:58, 55:13, 59:22, 67:2, 73:4, 94:5, 103:2, 108:2, 112:2, 112:4, 113:2, 114:4); Quran.com word timings (`chapter_recitations/{id}/{surah}?segments=true`, the practice word-highlight source); and Quran.com word-by-word audio (`audio.qurancdn.com/wbw/…`, the practice "tap to hear" source). Cached in `node_modules/.cache/munib-quran-pronunciation-eval/` (git-ignored); never committed.
- **Correct words:** every word of every kept reference clip, under 11 conditions — clean, speed 0.8× / 1.2×, pitch ±3 semitones, −24 dB, whisper-like band-limit, reverb, fan / car / crowd noise (the NF-3.20 S2 augmentations).
- **Spliced errors (labelled):** per clip, a middle word (≥ 3 letters) is **dropped** (its Quran.com span cut), a **span of three words is skipped**, and a word is **substituted** with the word-by-word recording of a **confusable word** (one letter of ح/ه, ع/ا, ص/س, ض/د, ط/ت, ق/ك, ذ/ز, ث/س, ظ/ز swapped, both words existing in the corpus) or, when the ayah has none, of another word; each splice is scored clean and with fan noise, reverb and pitch −3.
- **Cross-check:** a reference clip is kept only when the FastConformer greedy transcript (normalised distance ≤ 0.25) **and** the Zipformer phoneme transcript (where its corpus covers ≥ 50% of the words, distance ≤ 0.45) agree with the ayah text; a spliced clip only when **both** transcripts move away from the text. Quran Lab heads are not used (the SDK can't take external audio; no validated head applies to these splices).
- **Unit tests** use only synthetic log-prob matrices (`test-support/quran-pronunciation.ts`).

## 4. Release-gate status

- **S3 (GOP validity): MISSED.** False "Listen again" ≤ 2% **and** detection ≥ 60% could not both be met (best ≤ 2% setting: none; lowest false rate 2.85%). Confusable-letter substitutions are close to undetectable (≤ 22%) — the expected main risk: a model trained on recitation "hears" the expected text.
- **D24 fallback ships automatically** (`pronunciation-calibration.json` `mode: "skipped-only"`, generated by the eval, locked by `ayah-tokens.test.ts`): words are **Heard / Skipped or unclear / Not sure**, with 0.71% false flags on reference words. The full three-state Clear / Listen again path is implemented and unit-tested and turns on by itself if a future eval passes the gate.
- **S4 tokens:** compatible (§2); runtime uses the lattice. **S4 boundaries: MISSED** (p90 1,790 ms vs ≤ 80 ms). `alignmentBoundaryReliable()` returns false, so **NF-3.15 Phase B falls back to Phase A cards (D24)**; the per-word windows API still exists but must not drive per-word coaching while it is false.
- **Latency:** desktop only (above); on-device timing is an open QA item.
- **Copy / privacy gates:** met and unit-tested (§1 #4, #5). No claim of accuracy on real learners' voices appears anywhere in the app.
- **D11 review:** complete for the copy (§1). Re-run `pnpm --filter app quran-pronunciation:eval` on any model change (the lock test forces it).

## 5. NF-3.15 hand-off (D20, D25)

- `getFlaggedWords({ limit?, since? })` / `loadFlaggedWords()` (`lib/quran-pronunciation/flagged-words.ts`): recent "Listen again" words `{ surah, ayah, word (0-based study word), at }`, newest first, de-duplicated; `[]` when **Settings › Qur'an › Practice › "Use checked words in tajweed coaching"** (`companion.feedCoachingFromAssessment`, default on) is off.
- `getWordWindows(surah, ayah)`: per-word `{ word, startMs, endMs }` inside the person's last take of that ayah, from our own forced alignment — memory only, cleared when the check screen closes.
- `alignmentBoundaryReliable()`: whether S4's word-boundary gate (p90 ≤ 80 ms) was met; when false NF-3.15 Phase B falls back to Phase A cards (D24).
- Coaching copy must keep the same rule: a flagged word "wasn't clear", never "you broke the rule".

## 6. Store / privacy

- Microphone use reuses Qur'an practice's permission path; the explainer copy says everything stays on the device. Data safety still says audio is "not collected". FastConformer (NVIDIA, CC-BY-4.0) and the D18 mirror are already credited for Qur'an practice / hands-free tasbeeh.
- TV: hidden (`isPracticeAvailable()`); web: available because FastConformer is `webHosted` (D18).
